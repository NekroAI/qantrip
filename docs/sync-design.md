# 同步与端到端加密安全设计（v0.3）

PRD 第 9 章的实现设计，也是 PRD 第 18 章要求的"同步及端到端加密安全设计"交付物。

**状态**：v0.2 已按第一轮对抗性审查意见修订并定稿（负责人授权，docs/decisions.md D24）。v0.3 按 C2 客户端实现的第二轮对抗性审查修订：加入改为双向确认、记录增加写入者签名，并把实现中补充的细节（`set_recovery.bind`、状态记录条目格式、恢复密钥派生）写入设计。待负责人事后复核。审查意见与处理见附录 A、附录 B。

术语：

| 术语 | 含义 |
|---|---|
| 保险库（vault） | 一个用户的全部同步数据，对应一个账号 |
| Vault Key（VK） | 加密保险库中所有记录的对称密钥，按"密钥版本（epoch）"轮换 |
| 设备（device） | 一个已授权的客户端安装，持有自己的密钥 |
| 记录（record） | 同步的最小单位：一个模板、一项设置、一个 AI 供应商配置，或一台设备的状态记录 |
| 花名册（roster） | 经签名的设备与密钥事件日志，决定哪些公钥有权收到 VK |
| 信封（envelope） | 用某台设备或恢复密钥的公钥包装、并经发送方认证的 VK 钥匙环 |

---

## 1. 目标与范围

**同步的内容**（PRD 9.7）：用户模板（每个模板文件一条记录）、可同步的偏好设置、用户逐项开启同步的 AI 供应商配置（含 API Key，D3）。用户可以按类型选择同步范围：模板、设置、每个 AI 配置分别开关。

**不同步**：使用记录、全局快捷键、窗口与显示配置、系统权限状态、本机路径。

**安全目标**：

1. 服务端（包括数据库泄漏、运营者、托管平台）无法读取任何记录内容，包括模板名、别名、标签和设备名。
2. 主动作恶的服务端无法在不被察觉的情况下：篡改记录、挪用密文、回滚或隐藏记录、让客户端使用服务端选定的 VK、让客户端把 VK 发给未经用户批准的公钥、对设备隐藏撤销事件后继续让其读取新数据。
3. 撤销设备后，该设备拿不到之后写入的数据，也无法再写入被接受的数据。
4. 所有设备和恢复短语都丢失时，数据不可恢复；产品如实告知（PRD 9.5）。

**非目标**：防止服务端拒绝服务或删除数据；隐藏第 10 节所列元数据；远程删除已撤销设备上已解密的历史内容；防护已被攻破的设备。

## 2. 威胁模型

| 攻击者 | 能力 | 应对 |
|---|---|---|
| 被动服务端 / 数据库泄漏 | 读取全部存储 | 只存密文与最少元数据（第 4、10 节） |
| 主动服务端 | 任意修改响应、伪造设备与花名册、替换公钥与信封、重放、扣留、在信封里塞入自选的 VK | VK 承诺与认证信封（3.4），签名花名册与头部传播（6.1、4.3），用户输入校验码（6.2），状态记录防回滚与隐藏（4.4） |
| 拿到登录令牌的人（含盗取 GitHub 账号者） | 以用户身份调用 API：读写密文、发起加入请求 | 令牌无法解密；加入必须在已授权设备上手动输入校验码；回滚与隐藏由状态记录察觉 |
| 被撤销的设备（可能与服务端勾结） | 持有撤销前的全部 VK | 轮换 + `rotate_done` 后拒收旧 epoch（第 7 节）；头部传播防止撤销被隐藏 |
| 拿到一台已解锁设备的人 | 以该设备身份操作 | 夺取保险库的高危操作需要恢复短语签名（6.4） |
| 网络攻击者 | 中间人 | TLS；即使失效，也只等同于主动服务端 |

## 3. 密钥

### 3.1 设备密钥

每台设备首次启用同步时生成三把密钥，用途严格分离：

| 密钥 | 算法 | 用途 |
|---|---|---|
| 加密密钥 | X25519 | 接收和发送信封（HPKE Auth） |
| 花名册密钥 | Ed25519 | **只**签花名册条目、加入协议消息与记录的写入者签名（4.3），三者域前缀不同 |
| 认证密钥 | Ed25519 | **只**签登录挑战（自托管认证，第 9 节） |

- `device_id = Base32(SHA-256("qantrip/v1/device-id" || x25519_pub || roster_pub || auth_pub))[0..26]`，由公钥派生，不由服务端分配。
- 私钥存于系统安全存储（macOS 钥匙串 / Windows Credential Manager / Linux Secret Service），运行时交给 Rust 核心，核心不落盘。
- 任何签名都带固定的域前缀（见各处），客户端**永远不对服务端提供的原始字节签名**。

### 3.2 Vault Key

32 字节随机数，按 epoch 编号（从 1 开始）。"VK 钥匙环"是 `{epoch → VK}` 的集合。完成轮换（第 7 节）后旧 VK 从钥匙环中丢弃。

### 3.3 恢复短语

256 位熵，BIP39 编码为 24 个词（英文或简体中文词表）。不设口令，不用慢速 KDF。派生：

```
recovery_x  = HKDF-SHA256(entropy, info = "qantrip/v1/recovery/x25519")
recovery_s  = HKDF-SHA256(entropy, info = "qantrip/v1/recovery/ed25519")
```

`entropy` 是短语编码的 32 字节原始熵（解析短语、校验 BIP39 校验和后取回），**不**使用 BIP39 标准中经 PBKDF2-HMAC-SHA512 派生的 64 字节种子：熵本身已有 256 位，慢速 KDF 不增加安全性，还会让其他平台的实现多一个容易出错的步骤。

恢复公钥写入花名册（`set_recovery`，见 6.1 的 `bind`），轮换时任何在册设备都能为恢复公钥写新信封，不需要用户再输入恢复短语。

### 3.4 VK 承诺与认证信封

服务端不能生成 VK 后包装给设备：

- **承诺**：`genesis` 与每个 `rotate` 花名册条目包含
  `vk_commit = HKDF-SHA256(VK_e, info = "qantrip/v1/vk-commit" || vault_id || u32_be(epoch))`。
  花名册由在册设备签名，服务端无法伪造承诺。
- **信封**：HPKE（RFC 9180）**Auth 模式**，套件 DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / ChaCha20Poly1305。发送方用自己的 X25519 私钥认证，接收方据此确认信封来自某台在册设备。
  `info = "qantrip/v1/envelope" || vault_id || recipient_id || u32_be(epoch) || u32_be(roster_index)`。
  恢复信封的接收方为 `"recovery"`。
- **验证**：收到钥匙环后，接收方逐个 epoch 校验 `vk_commit`，并确认发送方在信封生成时在册；任何一项不符就整体拒绝，不用该钥匙环加密任何数据。

## 4. 记录

### 4.1 服务端存储的字段

```
records(vault_id, record_id, seq, epoch, ciphertext, deleted, updated_at, writer_device_id)
```

- `record_id`：客户端生成的 128 位随机数（base64url），不从模板名或内容派生。状态记录例外（4.4）。
- `seq`：服务端分配的保险库内单调递增序号，用于增量同步。
- `deleted`、`writer_device_id`：仅用于服务端的配额统计与墓碑清理。**客户端一律以明文中的值为准**，服务端的这两列不可信。

### 4.2 密文格式

```
ciphertext = ver(0x01) || nonce(24 字节随机) || XChaCha20-Poly1305(VK[epoch], nonce, aad, padded_plaintext)
aad        = "qantrip/v1/record" || ver || vault_id || record_id || u32_be(epoch)
```

- AAD 绑定版本字节、保险库、记录 ID 与 epoch。
- **长度填充**：明文填充到 256 字节的整数倍；超过 4 KiB 后填充到 2 的整数次幂。

### 4.3 明文结构

明文使用确定性 CBOR（字段按规范顺序编码，三个平台共用测试向量）：

```
{
  "type":    "template" | "setting" | "ai_provider" | "device_state",
  "counter": u64,                    // 该记录的逻辑版本，每次写入（包括重新加密）+1，不超过 2^53
  "deleted": bool,                   // 墓碑，以此为准
  "writer":  device_id,
  "roster":  { index: u32, head: 32 字节 },   // 写入者当时已验证的花名册头部
  "time":    unix 秒,                 // 仅供展示
  "body":    { … },
  "sig":     64 字节                  // 写入者签名（v0.3）
}
```

- **内容哈希** = SHA-256(除 `sig` 外全部字段的规范编码)，用于防回滚、分叉判定与状态记录（4.4）。
- **写入者签名**：`sig = Ed25519(writer 的花名册密钥, "qantrip/v1/record-sig" || 规范编码{ vault_id, record_id, epoch, counter, hash, writer, roster_index })`，`hash` 为内容哈希。签名在密文内部，服务端看不到。没有它，任何持有 VK 的设备（包括已被撤销、与服务端勾结的设备）都能以其他设备的名义写入。

客户端对每条解密后的记录执行：

1. 服务端字段的基本检查（`record_id` 格式、`seq > 0`），AEAD 校验（含 AAD），明文规范编码与 `counter ≤ 2^53`。
2. `writer` 在 `roster.index` 时刻必须在册；若 `roster.index` 超过本地已知头部，先拉取花名册并验证延伸；**拉不到就停止写入并报警**（防止服务端对本设备隐藏撤销等事件）。
3. 写入者签名：用 `writer` 在 `roster.index` 时刻在册的花名册公钥校验 `sig`。
4. 防回滚：`counter` 小于本地已知最大值 → 丢弃并报警；`counter` 相等但内容哈希不同 → 视为分叉，报警。
5. epoch 下限：若花名册中已有 `rotate_done(e)`，拒收 epoch < e 的记录。
6. 已移除的写入者：本地花名册中已有 `remove_device(writer)` 时，拒收本机之前没有接受过的任何版本（见第 7 节）。

### 4.4 设备状态记录（防回滚与隐藏）

每台在册设备维护一条状态记录：

- `record_id = Base64url(SHA-256("qantrip/v1/state" || vault_id || device_id))[0..22]`，任何设备都能算出。
- `body = { entries: { record_id → [max_counter, content_hash, deleted] } }`，每次该设备同步完成后更新。`deleted` 用于区分"墓碑按 180 天规则被清理"与"服务端隐藏记录"，否则墓碑清理后会持续误报。
- 创建保险库的设备在创建时立即写入自己的（空）状态记录。

新设备首次同步（以及所有设备每次全量对账）时，取所有在册设备状态记录的并集最大值：发现某条记录的 `counter` 落后、或某条应存在的记录缺失，即判定为回滚或隐藏并报警。必须存在状态记录的设备：写过本机已接受记录的在册设备、创建保险库的设备（仍在册时）、加入时批准本机的设备（6.2 的锚点：其状态记录不得早于锚点版本）。状态记录缺失本身也会报警；已移除设备的状态记录不再参与比对。已有设备发现自己的新版本被回滚时，自动重新推送。

### 4.5 记录类型

| 类型 | body | 本地对应 |
|---|---|---|
| `template` | `{ file_name, source }` | 模板目录中的一个 `.md` 文件（D11） |
| `setting` | `{ key, value }` | 一项可同步的偏好设置 |
| `ai_provider` | `{ id, protocol, base_url, api_key, model, params }` | 一个 AI 供应商配置（逐项开启，D3） |
| `device_state` | 见 4.4 | — |

- **API Key**：解密后只写入系统安全存储；本地同步缓存只保存密文，不保留明文。
- **关闭某个 AI 配置的同步**：写入该记录的墓碑，并提示用户这把 Key 已经同步到过其他设备，如需彻底收回应到供应商处更换。
- **版本历史**（PRD 9.6）：客户端在本地保留每个模板最近 20 个版本（含同步收到的版本），用于查看与恢复；服务端只保存最新版本（成本与元数据考虑）。
- **墓碑**：保留 180 天后服务端清理。设备离线超过 150 天后再同步，必须先做全量对账（4.4）再推送任何写入；`base_seq` 指向已清理的行时，服务端返回 `gone`，客户端转为全量对账。

## 5. 同步协议

接口位于 `/api/v1/vaults/{vault_id}`，需要设备访问令牌（第 9 节）。

### 5.1 版本检查（轻量）

```
GET /head  →  { seq, roster_index }
```

只读一行，用于判断是否需要拉取。客户端在应用启动、模板保存后、以及每 10 分钟（应用运行时）调用一次；唤起面板**不**直接触发同步，只在距离上次检查超过 2 分钟时顺带检查（避免把面板使用时间线暴露给服务端，也控制请求量）。

### 5.2 拉取

```
GET /changes?since={seq}&limit=200
→ { records: [{ record_id, seq, epoch, ciphertext, deleted }], next: seq | null, head: seq }
```

查询走 `(vault_id, seq)` 索引，只扫描变化的行。

### 5.3 推送

```
POST /records
{ writes: [{ record_id, base_seq | null, epoch, ciphertext, deleted, idempotency_key }] }   // 每批 ≤ 50 条
```

- 服务端逐条检查 `base_seq` 与当前 `seq` 一致才接受并分配新 `seq`；否则该条返回 `conflict` 与当前版本，其余照常处理。
- `idempotency_key` 让重试不产生重复写入（保留 24 小时）。
- 服务端校验 epoch 不小于该保险库记录在案的下限（7 节 `rotate_done` 后由客户端上报），这是对客户端规则的补充，不是安全依据。

### 5.4 花名册

```
GET  /roster?since={index}                       → { entries: [...] }
POST /roster   { expected_index, entry }         → 201 | 409（CAS：只有当前长度等于 expected_index 才追加）
```

### 5.5 冲突

以单条记录为粒度（PRD 9.6，不引入 CRDT）：内容相同直接采用；不同则对方版本写入原文件，本地版本另存为 `<名称>.conflict-<设备简称>-<时间>.md` 并在模板库中标记待合并。

## 6. 花名册与设备加入

### 6.1 签名花名册

只追加的签名日志：

```
entry = {
  index:   u32,
  prev:    SHA-256(上一条 entry 的完整规范编码，含 sig) | 32 字节零（第 0 条）,
  op:      "genesis" | "set_recovery" | "add_device" | "remove_device" | "rotate" | "rotate_done",
  subject: …,                       // 见下表
  signer:  device_id | "recovery",
  sig:     Ed25519(signer 的花名册密钥, "qantrip/v1/roster" || vault_id || 规范编码(entry 除 sig))
}
```

| op | subject | 签名者 |
|---|---|---|
| `genesis` | 第一台设备的三把公钥 + `vk_commit(epoch 1)` | 该设备 |
| `set_recovery` | 恢复 X25519 与 Ed25519 公钥 + `bind` | 创建时为第一台设备；之后只能由 `"recovery"` 签名 |
| `add_device` | 新设备的三把公钥 | 在册设备或 `"recovery"` |
| `remove_device` | device_id | 在册设备；移除除签名者外的最后一台设备时只能由 `"recovery"` 签名 |
| `rotate` | 新 epoch + `vk_commit` | 在册设备 |
| `rotate_done` | epoch | 发起该轮换的设备，或超时接管者 |

验证使用 Ed25519 严格校验（`verify_strict`）。客户端在本地保存已验证的头部（index 与哈希），新拉取的花名册必须从本地头部延伸，否则拒绝并报警。

**`set_recovery.bind`**：恢复 Ed25519 私钥对 `"qantrip/v1/recovery-bind" || vault_id || prev`（`prev` 即该条目的 `prev`）的签名，验证时用条目中的恢复公钥校验。用恢复短语加入的设备没有任何本地状态；没有这个绑定，服务端可以伪造一整条以自己设备为 genesis、但带有用户真实恢复公钥的花名册，再用自选 VK 写恢复信封。有了绑定，伪造花名册必须持有恢复私钥。

### 6.2 新设备加入（双向输入校验码）

适用于两台电脑之间。服务端只转发消息；N 是新设备，E 是已授权设备。四段消息依次为 commit、reply、reveal、result（确定性 CBOR）：

```
N: 生成三把密钥，n_N ← 32 字节随机
N → E: commit = { v: 1, c },  c = SHA-256("qantrip/v1/commit" || vault_id || pk_N || n_N)
E: 只接受 v = 1；回复时锁定 commit 的完整字节
E → N: reply = { pk_E, n_E, 完整花名册 }            （N 在公开 n_N 之前收到并锁定）
N: 验证花名册链、pk_E 在册，锁定 head
N → E: reveal = { pk_N, n_N }
E: 服务端当前的 commit 必须与锁定的逐字节相同，再校验 c
两端: SAS = 截取 40 位(SHA-256("qantrip/v1/sas" || vault_id || head || pk_N || pk_E || n_N || n_E))
      显示为 8 个 Base32 字符（如 K7QM-2XRA）
N 上：显示 SAS 与"请在已登录的设备上输入此校验码"，没有任何确认按钮
E 上：用户**手动输入** N 上显示的 SAS（不提供"一致吗？是"的按钮），不显示 N 的名称
E: 输入不符 → 本地计数，3 次后冷却 10 分钟
E: 以 CAS 追加 add_device(N)，发送 HPKE Auth 信封（钥匙环）
E → N: result = { 新花名册条目, 信封, epoch, roster_index, anchor }
       anchor = E 自己状态记录的 { seq, counter, hash }（尚未写过时为 null）
E 上：显示确认码 = 截取 40 位(SHA-256("qantrip/v1/join-confirm" || vault_id || SHA-256(commit)
      || SHA-256(reply) || SHA-256(reveal) || SHA-256(result) || u32_be(新 head index) || 新 head))
N: 验证新 head 是原 head 的延伸、含由 E 签名的 add_device(N)、信封来自 E、每个 epoch 的 vk_commit
N 上：用户**手动输入** E 上显示的确认码；不符 → 本地计数，3 次后冷却 10 分钟并取消本次加入
N: 确认码通过后，拉取服务端花名册，要求 N 将要采用的花名册（含 reply 中锁定的部分）是它的前缀；
   然后才采用花名册与钥匙环、合并本地模板并开始上传
N → E: 设备名称（HPKE Auth 加密），之后作为加密的设置记录同步
```

- 先承诺再公开，且 N 在公开 n_N 前已锁定 pk_E 与 head：攻击者无法离线穷举，在线尝试的成功率为 2⁻⁴⁰。E 锁定 commit 的字节，服务端不能在看到 n_E 之后再换承诺（否则可以离线穷举约 2⁴⁰ 次 SHA-256，让 SAS 恰好等于 N 显示的值）。
- 用户必须在 E 上输入校验码，盗用账号者反复发起请求也无法靠"顺手点批准"得逞。
- **反向确认**：只有 SAS 时，N 会采用任何交给它的花名册与钥匙环——服务端或盗用令牌者可以伪造一个以自己设备为 genesis 的保险库，N 无需任何用户操作就加入，并用攻击者的 VK 上传本地模板。确认码覆盖四段消息的完整字节与新的花名册头部，只能从真实 E 的屏幕上读到；N 在确认码通过之前**不向服务端写入任何数据**。确认码也认证了 result 中的 `anchor`。
- N 得到的 `anchor` 用于首次同步的对账（4.4）：服务端不能对新设备隐藏全部记录（包括状态记录）而不被察觉。
- 双方的进行中状态（含 n_N、n_E、锁定的 commit 与已收到的消息）保存在系统安全存储中，应用重启后可以继续；完成、过期、拒绝或失败时删除。
- 加入请求 10 分钟过期。

### 6.3 用恢复短语加入

输入恢复短语 → 派生恢复密钥 → 校验与花名册中最新 `set_recovery` 的公钥一致 → 解开最新恢复信封（信封明文包含生成时的花名册 index 与 head，客户端要求拉到的花名册不早于此，防止服务端给出旧前缀）→ 以 `signer = "recovery"` 签名 `add_device`。

**已知局限**：恢复的设备没有任何本地状态，"最新"只能以服务端给出的为准。服务端可以同时给出一个**较旧但真实**的花名册前缀和当时写入的旧恢复信封（两者彼此一致，校验都能通过）。后果：恢复的设备以旧的花名册加入，看不到之后的撤销与轮换；由于它随后以 CAS 追加 `add_device`，而真实花名册已经更长，追加会失败或形成分叉，其他设备会察觉（链校验、头部传播）。在当前设计下无法完全消除（需要服务端之外的新鲜度来源），记录在案；恢复后界面应提示用户在其他设备上核对设备列表。

### 6.4 高危操作

以下操作必须由恢复短语签名（用户需输入恢复短语），防止拿到一台已解锁设备的人夺取保险库：

- 创建之后更换恢复密钥（`set_recovery`）。
- 移除除操作者自己之外的最后一台设备。

## 7. 撤销与轮换

撤销设备 D：

1. 在册设备以 CAS 追加 `remove_device(D)`，并通知服务端吊销 D 的访问令牌。
2. 生成新 VK，以 CAS 追加 `rotate(e+1, vk_commit)`。**花名册追加成功后**才进行后续步骤；CAS 失败说明有并发操作，重新拉取花名册后重来。
3. 为剩余每台设备和恢复公钥写入 HPKE Auth 信封（钥匙环含新旧 VK；恢复信封带当前花名册 head）。
4. 把所有记录用新 VK 重新加密，`counter` +1，推送。
5. 追加 `rotate_done(e+1)`。此后客户端拒收 epoch ≤ e 的记录，并从钥匙环中丢弃旧 VK。
6. 若 D 曾同步过 AI 配置，列出受影响的供应商，提示到供应商处作废并更换 API Key（PRD 9.5）。

- 在 `rotate` 与 `rotate_done` 之间，新写入一律使用新 epoch；旧 epoch 的新版本只接受由当时在册设备写入、签名有效的（4.3）。
- **重新加密只针对轮换开始前已接受的版本**：客户端为每个已接受的版本记下当时的本地花名册长度，第 4 步只重新加密在 `rotate` 条目之前就已接受的版本。轮换窗口内才第一次出现的旧 epoch 版本照常校验与接受，但不被"洗白"到新 epoch；若它来自仍在册的设备，写入者发现自己的版本停留在作废的 epoch 时，用新密钥重新推送。
- 被移除设备写入、而本机此前没有接受过的版本一律拒收（4.3 第 6 步）。代价：被撤销设备在撤销前最后一刻的写入，如果其他设备还没来得及接受，就会丢失。
- `counter` 已达 2^53 的记录不再修改，也不阻塞轮换（留在旧 epoch，`rotate_done` 后作废）。
- **接管**：`rotate` 之后 24 小时内没有 `rotate_done`（例如发起设备崩溃或丢失），任何在册设备都可以发起下一次轮换（e+2）并完成，避免保险库被卡住。
- 用户手动轮换（不撤销设备）走同样流程。

## 8. 客户端能察觉与不能察觉的服务端行为

| 服务端行为 | 结果 |
|---|---|
| 修改、伪造、挪用密文 | AEAD 校验失败，丢弃并报警 |
| 在信封中塞入自选的 VK | `vk_commit` 或 HPKE 认证失败，拒绝 |
| 返回旧版本 / 隐藏记录 | 计数器或状态记录比对发现，报警 |
| 伪造、分叉、截断花名册 | 链校验失败或头部传播发现，停止写入并报警 |
| 冒充已授权设备、替换加入请求中的公钥 | 校验码无法在真实设备上输入成功，加入不会完成 |
| 在 E 回复后替换承诺；伪造保险库或伪造 result 交给新设备 | E 比对锁定的承诺；新设备拿不到真实 E 显示的确认码，不采用、不上传 |
| 与被撤销设备勾结，在轮换窗口内写入或冒充其他设备 | 写入者签名与"已移除写入者"规则拒收，重新加密不会洗白 |
| 对新设备隐藏全部记录 | 创建者与批准者的状态记录必须存在，批准者的锚点由确认码认证 |
| 扣留其他设备的最新写入 | 由状态记录与头部传播在下次对账时发现；在此之前只能表现为延迟 |
| 拒绝服务、删除数据 | 无法阻止；本地数据始终完整可用，可重新推送 |

## 9. 访问控制（与加密分离）

登录只决定能否调用 API，与能否解密无关（PRD 9.4）。

- **官网登录**：GitHub OAuth，网页会话 Cookie（HttpOnly、Secure、SameSite=Lax），服务端只存令牌哈希。
- **桌面端登录**：浏览器授权码 + PKCE（S256），回调到本机回环地址；访问令牌 1 小时，刷新令牌 90 天并轮换，服务端只存哈希。每个令牌绑定一台设备。
- **撤销**：撤销设备时吊销其令牌；官网"设备"页也可直接吊销访问权（花名册的移除仍需在已授权设备上完成，页面会说明）。
- **自托管认证（C4）**：设备以**认证密钥**签名 `"qantrip/v1/auth" || origin || vault_id || server_nonce || client_nonce` 换取令牌；不依赖 OAuth。
- **后端切换**：客户端可以填写自部署的后端地址；切换后端等同于新建保险库，不迁移密钥。
- **重置保险库**（所有设备与恢复短语都丢失时）：官网登录后可删除整个保险库（二次确认，明确告知数据不可恢复），然后在设备上重新创建。删除只影响密文，不影响任何设备上的本地模板。

## 10. 服务端可见的元数据

官网安全页使用同一份清单：

- **账号**：GitHub 用户 ID、用户名、头像、登录时间、IP（Cloudflare 日志）。
- **设备**：数量、公钥、加入与最后活跃时间。设备名称加密存储。
- **花名册**：事件类型与时间（加入、撤销、轮换、是否使用过恢复短语）。
- **记录**：数量、密文长度（已填充到档位）、写入时间、写入设备、epoch、删除标记；由此可以推断出哪台设备编辑过哪些记录、大致的记录类型分布。
- **同步**：版本检查与拉取的时间和频率（已与面板唤起解耦，见 5.1）。

服务端**看不到**：模板名、别名、标签、正文、参数、设置内容、AI 配置与 API Key、设备名称、恢复短语。

## 11. 成本模型（Workers Paid，5 美元 / 月）

**包含额度**：每月 1000 万次请求、3000 万 CPU 毫秒；D1 每月 250 亿行读取、5000 万行写入、5 GB 存储；R2 10 GB 存储。超出部分按量计费，不会因单个用户失控（配额与限流兜底）。

**单台活跃设备的月用量估算**（每天开机 10 小时）：

| 来源 | 次数 / 月 | D1 行读取 | D1 行写入 |
|---|---|---|---|
| 版本检查（每 10 分钟） | ≈ 1,800 | 1 / 次 | 0 |
| 有变化时的拉取 | ≈ 300 | ≈ 变化行数 | 0 |
| 推送（每次约 3 行写入） | ≈ 300 | ≈ 3 / 条 | ≈ 3 / 条 |
| 合计 | ≈ 2,400 请求 | ≈ 1 万行 | ≈ 1,000 行 |

- **请求**是首先触顶的维度：1000 万次约可支撑 **4,000 台活跃设备**；之后每增加 1000 台活跃设备，约增加 0.7 美元 / 月。
- **D1 读写**远低于额度（4,000 台设备约 4000 万行读取、400 万行写入）。
- **存储**：一个典型保险库（50 个模板）约 100–200 KB，5 GB 可容纳约 3 万个保险库。

**硬性限制**（防止滥用导致成本失控）：

| 项 | 限制 |
|---|---|
| 单条记录密文 | ≤ 256 KiB |
| 单个保险库 | ≤ 10 MiB、≤ 5,000 条记录 |
| 每个账号 | 1 个保险库、≤ 10 台在册设备 |
| 读请求 | 每个令牌每分钟 120 次 |
| 写请求 | 每个令牌每分钟 60 次，每批 ≤ 50 条 |
| 新建保险库 | 每个 IP 每天 ≤ 5 个 |
| 清理任务 | 每天一次，每次最多处理 1,000 行（墓碑、过期加入请求、过期幂等键） |

所有 D1 查询都按主键或复合索引访问，不存在随数据量增长的全表扫描。

## 12. 实现选型

**客户端（Rust 核心）**：`chacha20poly1305`（XChaCha20-Poly1305）、`hpke`（RFC 9180，Auth 模式）、`ed25519-dalek`（`verify_strict`）、`x25519-dalek`、`sha2`、`hkdf`、`bip39`（英文与简体中文词表）、`ciborium`（加规范化）、`rand_core::OsRng`、`zeroize`。纯 Rust，三个平台交叉编译不引入 C 依赖；不自行组合原语。

**服务端（`apps/cloud/`）**：Hono + D1。服务端代码不包含任何解密逻辑；日志不记录密文、令牌与请求体。服务端只做格式与配额校验，不承担任何安全判定。

**客户端对服务端输入的处理**（v0.3）：

- **不回显服务端文本**：告警与错误信息只由本地固定文本和本机已验证花名册中的设备简称组成，不包含服务端返回的说明文字、记录 ID、epoch 标签或解析细节。服务端错误码只保留 `[a-z0-9_]{1,64}`，说明文字按错误码取本地文本。这同时防止服务端用大量不同的告警挤掉真正的告警。
- **大小上限**：花名册单次响应 ≤ 1,000 条、单条 ≤ 16 KiB、总数 ≤ 10,000 条；一次拉取的记录总数 ≤ 20,000；每次列出加入请求最多处理 3 个；服务端分配的 ID 只接受 `[A-Za-z0-9_-]{1,64}`。
- **重新校验**：因安全原因停止写入后，用户可以触发"重新校验"：重新拉取完整花名册（本机已验证的花名册必须是它的前缀）与全部记录并逐条校验，这一轮没有再次触发停止写入时才解除。
- **模板文件**：文件名比较按 NFC 规范化后转小写（与 APFS / NTFS 的默认行为一致），避免两条记录落到同一个文件；读取不跟随符号链接；文件名不得含 Unicode 控制字符与格式字符（Cf，如双向覆盖、零宽字符）。

## 附录 B：C2 客户端实现的对抗性审查（v0.3）与处理

审查对象为 Rust 核心中的同步客户端（`core/src/sync/`），假设服务端完全恶意。每项问题的概念验证攻击都已改写为回归测试（`core/src/sync/tests/review.rs`），断言攻击现在被拒绝。

| 编号 | 级别 | 问题 | 处理 |
|---|---|---|---|
| C1 | 严重 | E 批准时重新从服务端读取 commit，没有锁定 N 的承诺。n_E 公开后，服务端可离线穷举约 2⁴⁰ 次 SHA-256 选出与 N 所显示 SAS 一致的 (pk_A, n_A)，替换 commit 与 reveal；用户输入正确的校验码反而让 E 加入攻击者并发出 VK | E 回复时保存 commit 的完整字节，批准时逐字节比对，不符即中止并报警；只接受 `v = 1`（6.2） |
| C2 | 严重 | N 不经用户确认就采用交给它的花名册与钥匙环：服务端可伪造以自己设备为 genesis 的保险库让 N 加入，N 用攻击者的 VK 上传模板；盗用令牌者同样可以（服务端允许账号的任何令牌写 reply / result） | 双向确认：E 批准后显示覆盖完整消息与新头部的确认码，用户在 N 上输入；N 在通过之前不采用、不写入，错误 3 次冷却；采用前要求服务端花名册以 reply 中的花名册为前缀（6.2） |
| H1 | 高 | 记录没有写入者签名：被撤销设备与服务端勾结，可在轮换窗口内以任意写入者的名义写入，`reencrypt_all` 再把它洗白到新 epoch | 明文内的 Ed25519 写入者签名（4.3）；拒收被移除写入者的新版本；重新加密只针对轮换开始前已接受的版本（第 7 节） |
| M1 | 中 | 只对本机已有记录的写入者要求状态记录：服务端对新设备隐藏全部记录（含状态记录）时没有任何告警 | 创建者在创建时写入状态记录，对账要求创建者与批准者的状态记录存在；result 携带批准者状态记录锚点，由确认码认证（4.4、6.2） |
