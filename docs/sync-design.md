# 同步与端到端加密安全设计（草案 v0.1）

PRD 第 9 章的实现设计，也是 PRD 第 18 章要求的"同步及端到端加密安全设计"交付物。状态：**待负责人确认**，确认前不实现 C1–C3（docs/decisions.md D23）。

本文用到的术语：

| 术语 | 含义 |
|---|---|
| 保险库（vault） | 一个用户的全部同步数据，对应一个账号 |
| Vault Key（VK） | 加密保险库中所有记录的对称密钥，按"密钥版本（epoch）"轮换 |
| 设备（device） | 一个已授权的客户端安装，持有自己的密钥对 |
| 记录（record） | 同步的最小单位，一个模板、一组设置或一个 AI 供应商配置 |
| 花名册（roster） | 经签名的设备增删日志，决定哪些公钥有权收到 VK |
| 信封（envelope） | 用某个公钥或恢复密钥包装后的 VK |

---

## 1. 目标与范围

**同步的内容**（PRD 9.7）：用户模板（每个模板文件一条记录）、可同步的偏好设置、用户逐项开启同步的 AI 供应商配置（含 API Key，D3）。

**不同步**：使用记录（`usage.json`）、全局快捷键、窗口与显示配置、系统权限状态、本机路径。

**安全目标**：

1. 服务端（包括数据库泄漏、运营者、托管平台）无法读取任何记录的内容，包括模板名、别名、标签和设备名。
2. 主动作恶的服务端无法在不被察觉的情况下：篡改记录、把某条记录的密文挪到另一条记录、把记录回滚到旧版本、让客户端把 VK 发给未经用户批准的公钥。
3. 撤销设备后，该设备拿不到之后写入的数据。
4. 所有设备和恢复短语都丢失时，数据不可恢复；产品如实告知这一点（PRD 9.5）。

**非目标**：

- 防止服务端拒绝服务、删除数据或扣留最新更新（服务端始终可以不响应；第 8 节说明客户端能察觉到什么）。
- 隐藏流量元数据（第 10 节列出服务端能看到什么）。
- 远程删除已撤销设备上已经解密并保存的历史内容（PRD 9.5）。
- 防护已被攻破的客户端设备（恶意软件可以直接读取解密后的模板）。

## 2. 威胁模型

| 攻击者 | 能力 | 设计应对 |
|---|---|---|
| 被动服务端 / 数据库泄漏 | 读取 D1 与 R2 中的全部数据 | 只存密文与最少元数据（第 4、10 节） |
| 主动服务端 | 任意修改返回给客户端的数据、伪造设备、替换公钥、重放旧密文、扣留更新 | 记录认证加密与 AAD 绑定（第 4 节），签名花名册（第 6 节），加入时的短校验码（第 6.2 节），记录计数器防回滚（第 4.3 节） |
| 网络攻击者 | 中间人 | TLS；即使 TLS 失效，也只等同于"主动服务端" |
| 拿到登录令牌的人 | 以用户身份调用 API | 令牌只能访问密文，无法解密；不能把自己加入花名册（需要已有设备在本机核对校验码并签名） |
| 被撤销的设备 | 持有撤销前的全部密钥 | 撤销后立即轮换 VK 并重新加密（第 7 节） |
| 拿到恢复短语的人 | 等同于拥有保险库 | 恢复短语只在本机生成和显示，提示用户离线保存 |

## 3. 密钥层级

```
恢复短语（24 个词，256 位熵）
  └─ HKDF → 恢复密钥对（X25519 加密 + Ed25519 签名）
         └─ 恢复信封：VK 钥匙环（各 epoch 的 VK）

设备 A 密钥对（X25519 + Ed25519，私钥存于系统安全存储）
  └─ 设备信封：VK 钥匙环

VK（epoch n，32 字节随机）
  └─ 加密所有记录（XChaCha20-Poly1305）
```

- **设备密钥**：每台设备首次启用同步时生成一对 X25519（收信封）和一对 Ed25519（签花名册）。私钥存放在 macOS 钥匙串 / Windows DPAPI（Credential Manager）/ Linux Secret Service，不离开本机，不上传。
- **VK**：32 字节随机数，按 epoch 编号（从 1 开始）。撤销设备或用户手动轮换时生成新 epoch。
- **VK 钥匙环**：信封里装的是"截至当前 epoch 的全部 VK"，这样新设备也能解开尚未重新加密的旧记录。轮换后会尽快把所有记录重新加密到最新 epoch（第 7 节），旧 VK 只用于过渡。
- **恢复短语**：首次启用同步时生成，256 位熵，用 BIP39 词表编码为 24 个词（提供英文与简体中文词表）。不设口令，不需要慢速 KDF，因为熵已经足够。由恢复短语经 HKDF 派生一对恢复密钥（X25519 + Ed25519），**公钥**存入保险库并写进花名册。轮换 VK 时，任何设备都能用恢复公钥重新包装新钥匙环，不需要用户再输入一次恢复短语。

派生（HKDF-SHA256，salt 为空，info 区分用途）：

```
seed       = BIP39 熵（32 字节）
recovery_x = HKDF(seed, info = "qantrip/v1/recovery/x25519")   → X25519 私钥
recovery_s = HKDF(seed, info = "qantrip/v1/recovery/ed25519")  → Ed25519 种子
```

## 4. 记录

### 4.1 服务端存储的字段

```
records(vault_id, record_id, seq, epoch, ciphertext, deleted, updated_at, writer_device_id)
```

- `record_id`：客户端生成的 128 位随机数（base64url），**不从模板名或内容派生**（PRD 9.3 第 9 条）。
- `seq`：服务端分配的保险库内单调递增序号，用于增量同步。
- `epoch`：加密所用 VK 的版本。
- `deleted`：删除标记（墓碑）。删除也是一次带密文的写入，见 4.3。
- `writer_device_id`：写入设备，用于审计与冲突提示。

### 4.2 密文格式

```
ciphertext = version(1 字节 = 0x01) || nonce(24 字节，随机) || XChaCha20-Poly1305(VK[epoch], nonce, aad, padded_plaintext)
aad        = "qantrip/v1/record" || vault_id || record_id || u32_be(epoch)
```

- AAD 绑定保险库、记录 ID 与 epoch：服务端无法把一条记录的密文挪到另一条记录或另一个保险库，也无法谎报 epoch。
- `seq` 不进入 AAD（由服务端分配，写入时客户端尚不知道），防回滚靠明文内的计数器（4.3）。
- **长度填充**：明文先填充到 256 字节的整数倍，超过 4 KiB 后填充到 2 的整数次幂，减少按密文长度推测内容的可能。

### 4.3 明文结构

明文使用 CBOR（确定性编码）：

```
{
  "type":    "template" | "setting" | "ai_provider",
  "counter": u64,          // 该记录的逻辑版本，每次写入 +1
  "deleted": bool,         // 墓碑
  "device":  device_id,    // 写入设备
  "time":    unix 秒,       // 写入设备的本地时间，仅供展示
  "body":    { … }          // 按类型定义，墓碑为空
}
```

- **防回滚**：客户端为每条记录保存见过的最大 `counter`。服务端返回的密文若 `counter` 更小，视为回滚，丢弃并在同步状态中报警。
- **墓碑**：删除写入一条 `deleted = true` 的新版本，服务端同时把 `deleted` 列置真，以便所有设备都收到删除。墓碑保留 180 天后由服务端清理。

### 4.4 记录类型

| 类型 | body | 本地对应 |
|---|---|---|
| `template` | `{ file_name, source }` | 模板目录中的一个 `.md` 文件（D11） |
| `setting` | `{ key, value }` | 一项可同步的偏好设置 |
| `ai_provider` | `{ id, protocol, base_url, api_key, model, params }` | 一个 AI 供应商配置（逐项开启，D3）；`base_url` 支持本机覆盖 |

本地维护一份映射索引（模板文件 ↔ `record_id` 与最近同步的 `counter`、内容哈希），不进入同步。

## 5. 同步协议

所有接口位于 `/api/v1/vaults/{vault_id}`，需要设备访问令牌（第 9 节）。

### 5.1 拉取

```
GET /changes?since={seq}&limit=500
→ { records: [{ record_id, seq, epoch, ciphertext, deleted }], next: seq | null, head: seq }
```

客户端解密并逐条校验：AAD、计数器、记录类型。任一校验失败，该条记录不应用，同步状态显示警告。

### 5.2 推送

```
POST /records
{ writes: [{ record_id, base_seq | null, epoch, ciphertext, deleted, idempotency_key }] }
```

- `base_seq` 是客户端修改时基于的服务端版本（新记录为 null）。
- 服务端在一个事务中逐条检查：当前 `seq` 与 `base_seq` 一致才接受，并分配新的 `seq`；不一致则该条返回 `conflict` 和当前版本，**其余条目照常处理**。
- `idempotency_key` 让断网重试不会产生重复写入。
- 写入使用的 `epoch` 必须是当前 epoch（轮换期间除外，见第 7 节）。

### 5.3 冲突

以单条记录为粒度（PRD 9.6，不引入 CRDT）。客户端收到冲突后：

1. 拉取对方版本并解密。
2. 内容相同则直接采用。
3. 内容不同：本地保留双方版本——对方版本写入原文件，本地版本另存为 `<名称>.conflict-<设备简称>-<时间>.md`，并在模板库中标记待合并。用户合并后作为新版本推送。

### 5.4 节奏

首版不使用 Durable Objects：应用启动、唤起面板、模板保存后触发同步，另外每 5 分钟轮询一次。同步永远不阻塞面板的唤起、搜索与插入（PRD 8.1）。

## 6. 设备与花名册

### 6.1 签名花名册

花名册是一条只追加的签名日志，决定哪些公钥属于这个保险库：

```
entry = {
  index: u32,
  prev:  SHA-256(上一条 entry 的规范编码) | 全零（第 0 条）,
  op:    "genesis" | "add_device" | "remove_device" | "set_recovery" | "rotate",
  subject: { device_id, x25519_pub, ed25519_pub } | { recovery_x25519_pub, recovery_ed25519_pub } | { epoch },
  signer: device_id | "recovery",
  sig:   Ed25519(signer 的私钥, "qantrip/v1/roster" || vault_id || 规范编码(entry 除 sig 外))
}
```

- **第 0 条（genesis）**：第一台设备在创建保险库时自签，并紧接着写入 `set_recovery`。
- 每台设备在本地保存已验证的花名册头部哈希。从服务端拉取花名册时，必须能从本地已知的头部按链延伸，并逐条验证签名与签名者在当时是否在册；否则拒绝并报警（防止服务端分叉或伪造花名册）。
- **客户端只向花名册中在册的公钥包装 VK**。服务端即使在设备列表里塞入自己的公钥，也拿不到 VK。
- 新设备第一次见到花名册时，信任来源是加入流程中经用户核对的校验码（6.2），校验码同时覆盖花名册头部哈希。

### 6.2 新设备加入：短校验码比对

适用于两台电脑之间（无法扫码）。流程中服务端只转发消息：

```
新设备 N                              服务端                         已授权设备 E
生成密钥对，随机 n_N
commit = SHA-256(pk_N || n_N) ──────→ 创建加入请求 ──────────────→  显示"新设备请求加入"
                                                                    随机 n_E
                         ←────────────── 转发 n_E ←──────────────── 发送 n_E
公开 pk_N, n_N ─────────────────────→ 转发 ─────────────────────→  校验 commit
                                                                    
两端计算 SAS = 截取 32 位( SHA-256("qantrip/v1/sas" || vault_id || roster_head || pk_N || pk_E || n_N || n_E) )
显示为 8 位十六进制（如 4F2A-9C11），用户核对两台设备上是否一致

用户在 E 上点"批准" ─────────────────────────────────────────────→ E 签名 add_device(N)，
                                                                    用 N 的 X25519 公钥包装 VK 钥匙环
```

- 先承诺再公开（commitment），攻击者无法离线搜索出与真实校验码相同的伪造公钥，每次尝试的成功率为 1/2³²。
- 校验码里包含 `roster_head`：N 由此确认自己拿到的花名册与 E 看到的一致。
- 加入请求 10 分钟过期；同一保险库同时只允许一个进行中的请求；连续失败触发冷却。

### 6.3 用恢复短语加入

手边没有其他已授权设备时：输入恢复短语 → 派生恢复密钥 → 校验与花名册中 `set_recovery` 的公钥一致 → 解开最新的恢复信封 → 以 `signer = "recovery"` 签名 `add_device`，把本机加入花名册。

## 7. 撤销与轮换

撤销设备 D（在任意在册设备上操作）：

1. 签名 `remove_device(D)`，并通知服务端吊销 D 的访问令牌（第 9 节），D 之后无法拉取任何数据。
2. 生成新 epoch 的 VK，签名 `rotate(epoch)`。
3. 向花名册中剩余的每台设备和恢复公钥各写一个新信封（钥匙环含新旧 VK）。
4. 把所有记录用新 VK 重新加密并推送（数据量小，一次性完成；中断后可续传）。
5. 若 D 曾同步过 AI 配置，列出受影响的供应商，提示用户到供应商处作废并更换 API Key（PRD 9.5）——轮换 VK 无法保护 D 已经取得的 Key。

轮换期间写入新记录一律使用新 epoch；服务端接受旧 epoch 的写入直到第 4 步完成，之后拒绝。

## 8. 客户端能察觉与不能察觉的服务端行为

| 服务端行为 | 结果 |
|---|---|
| 修改、伪造、挪用密文 | AEAD 校验失败，丢弃并报警 |
| 返回某条记录的旧版本 | 计数器回退，丢弃并报警 |
| 伪造或分叉花名册 | 链校验失败，拒绝并报警 |
| 替换加入请求中的公钥 | 两端校验码不一致，用户拒绝 |
| 不返回最新的写入（扣留） | **无法完全察觉**；其他设备写入的内容可能延迟出现。客户端会显示"上次成功同步时间"，并在本机已知的头部 `seq` 回退时报警 |
| 拒绝服务、删除数据 | 无法阻止；本地数据始终完整可用（Local-first），可重新推送 |

## 9. 访问控制（与加密分离）

登录只决定"能不能调用 API"，与能否解密无关（PRD 9.4）。

- **官网登录**：GitHub OAuth，网页会话（沿用 `nekro-nxt-community` 的 `web_sessions`）。
- **桌面端登录**：浏览器授权码 + PKCE，回调到本机回环地址；签发访问令牌（1 小时）与刷新令牌（90 天，轮换），服务端只存哈希（沿用 `instance_grants` 的设计）。每个令牌绑定一台设备。
- **撤销**：撤销设备时同时吊销其令牌；网页的"设备"页面也可直接吊销（只能吊销访问权，花名册的签名删除需要在已授权设备上完成，网页会提示这一点）。
- **自托管认证（C4）**：不依赖 OAuth 的模式——设备用 Ed25519 私钥对挑战签名换取令牌，花名册即访问控制列表。
- **后端切换**：客户端设置中可以填写自部署的后端地址；切换后端等同于创建新保险库，不迁移密钥。

## 10. 服务端可见的元数据

如实告知用户（PRD 9.3），官网安全页使用同一份清单：

- 账号身份（GitHub 用户 ID、用户名、头像）与登录时间。
- 设备数量、每台设备的公钥、加入与最后活跃时间、IP 地址（Cloudflare 日志）。**设备名称加密存储，服务端看不到。**
- 记录数量、每条记录的密文长度（已填充到固定档位）、写入时间、写入设备、删除标记。
- 同步的时间与频率。

服务端**看不到**：模板名、别名、标签、正文、参数、设置内容、AI 配置与 API Key、设备名称、恢复短语。

## 11. 实现选型

**客户端（Rust 核心，三个平台共用）**：

| 用途 | 选型 |
|---|---|
| 记录加密 | `chacha20poly1305`（XChaCha20-Poly1305，RustCrypto） |
| 信封 | HPKE（RFC 9180，`hpke` crate：DHKEM(X25519, HKDF-SHA256) + ChaCha20Poly1305，base 模式） |
| 签名 | `ed25519-dalek` |
| 哈希与派生 | `sha2`、`hkdf` |
| 恢复短语 | `bip39`（英文与简体中文词表） |
| 编码 | `ciborium`（确定性 CBOR 编码，由我们对字段顺序做规范化） |
| 随机数 | `rand_core::OsRng` |
| 内存 | `zeroize`，密钥类型实现 Drop 清零 |

选择纯 Rust 实现而不绑定 libsodium：三个平台交叉编译简单，不引入 C 依赖；所选 crate 均为生态中广泛使用、经过公开审计或大规模使用的实现。不自行组合原语，信封直接使用标准化的 HPKE。

**密钥存储**：设备私钥由平台外壳存入系统安全存储，运行时交给 Rust 核心；核心不落盘任何私钥。

**服务端（`apps/cloud/`）**：Hono + D1，SQL 迁移；服务端代码中不出现任何解密逻辑，日志不记录密文与令牌。

## 12. 测试与审查

- **测试向量**：记录加密、信封、花名册签名、SAS 计算各提供固定向量，三个平台的实现必须一致。
- **恶意服务端模拟**：在测试中替换服务端，逐项验证第 8 节表格中的每一行（篡改、挪用、回滚、伪造花名册、替换公钥）都被察觉。
- **服务端契约测试**：`vitest-pool-workers` 覆盖冲突语义、幂等、配额与权限隔离（一个用户无法访问另一个保险库）。
- **审查**：本文先由独立审查（对抗性视角）过一遍；正式开放同步前，邀请外部安全审查。

## 13. 待定

1. 短数字码配对（PAKE，如 CPace），用于手机等能扫码或只能输入短码的场景。
