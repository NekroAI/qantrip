# 1. 产品概述

## 1.1 产品定位

Nekro Qantrip（下称 Qantrip）是一款面向 AI 编程及日常 AI 使用场景的跨平台 Prompt 快捷输入与管理工具。

用户可以通过全局快捷键唤起轻量级命令面板，快速查找、组合和生成预设 Prompt，并将结果直接插入当前应用。

产品支持参数化模板、智能搜索、实时补全、可视化编辑、AI 辅助修改以及跨设备端到端加密同步。

应用应独立于具体 AI 服务及开发工具，可用于 Claude Code、Codex、Cursor、VS Code、终端、浏览器及其他支持文本输入的软件。

## 1.2 核心价值

1. **极致快捷：** 将高频 Prompt 输入操作压缩到尽可能少的按键。
2. **高度灵活：** 使用变量、参数、条件和组合机制减少重复模板。
3. **易于发现：** 用户无需记忆全部命令和参数，界面提供渐进式提示。
4. **开箱即用：** 内置经过整理的高质量 Prompt 模板和交互示例。
5. **AI 友好：** 允许 AI 通过自然语言创建、修改、优化和组织模板。
6. **跨平台一致：** 在 macOS、Windows、Linux 上提供一致的功能和符合平台习惯的体验。
7. **多设备同步：** 使用 Cloudflare 构建可自托管的加密同步服务。
8. **隐私优先：** 用户数据在本地加密，服务器只保存无法自行解密的密文。
9. **开放生态：** 完全开源、支持社区贡献和扩展，不绑定专有服务。

## 1.3 产品边界

本产品不以替代 IDE、AI 编程代理、终端、通用启动器或 AI 聊天客户端为目标。

核心职责是高效管理、生成及插入 Prompt。

所有核心模板操作必须能够离线完成，不得依赖 AI API 或云服务才能正常使用。

## 1.4 竞品参照与差异化（v0.2 新增）

| 产品 | 相关能力 | 本产品的差异 |

## 1.5 命名（v0.3 新增）

**Qantrip** = Q + cantrip。Cantrip 是 D&D 中的"戏法"：不消耗资源、可以随手反复施放的小法术，对应高频、一键调用的 Prompt（中文 AI 圈常把 Prompt 称为"咒语"）。首字母 C 换成 Q，呼应唤起快捷键中的 Q 键：**按 Q 施放一个戏法**。

- 中文称呼：戏法。模板在面向用户的文案中可称为"戏法"，模板库可称为"魔导书"。
- 读音与 cantrip 相同。README 首行应点明这个拼写来源，避免被当作拼写错误。
- 归属 NekroAI 组织，沿用 `nekro-<名词>` 的仓库命名惯例。
- 命名时的检索结果（2026-10）：GitHub 无同名仓库，Homebrew cask / formula 未被占用。

# 2. 目标用户与使用场景

主要用户包括：

- 高频使用 Claude Code、Codex 等 AI 编程代理的开发者。
- 经常使用 Cursor、VS Code 等 AI IDE 的开发者。
- 需要维护大量重复提示词的 AI 深度用户。
- 同时使用多台电脑及不同操作系统的用户。
- 希望集中管理个人或团队 Prompt 规范的用户。

### 典型场景

> 下列场景中的"唤起快捷键"指用户配置的全局快捷键，默认值见 3.1。

**场景 A：简单快捷输入**

用户按下唤起快捷键，输入 `zh`，按下 Enter。

应用自动插入：

> 帮我翻译成中文。

**场景 B：代码审查**

用户在 Claude Code 或 Codex 中唤起面板，输入 `r` 并确认。

应用自动插入预设的代码审查 Prompt。

**场景 C：参数化审查**

用户输入：

`r --scope=staged --strict --focus=security`

应用生成针对 Git 暂存区的严格安全审查 Prompt。

**场景 D：临时附加要求**

用户输入：

`r security 重点检查认证和权限模块`

`security` 与模板声明的位置参数 `focus` 的候选值精确匹配，被解析为参数；从第一个无法解析为参数的词 `重点检查…` 开始，其后全部作为本次生成的附加要求。解析规则见 `docs/input-grammar.md`。

**场景 E：AI 调整模板**

用户打开某个模板，通过自然语言要求 AI 新增参数、优化指令或合并其他模板。确认修改预览后，保存到模板库。

**场景 F：多设备同步**

用户在 Mac 上编辑模板后，Windows 和 Linux 设备在联网时自动同步更新；离线时继续使用本地版本。

# 3. 全局唤起与命令面板

## 3.1 全局入口（v0.2 修订）

**默认快捷键：** 保留 Q 键以呼应产品名，但按平台使用不同修饰键：

| 平台 | 默认候选 | 说明 |
|---|---|---|
| macOS | `⌃Q` | macOS 的退出是 `⌘Q`，`⌃Q` 基本空闲。终端的 XON 流控影响很小 |
| Windows / Linux | `Alt+Q` | 不触发"退出"。需验证 Office 中 `Alt+Q`（搜索 / 告诉我）等冲突 |

**不使用的组合：**

- Windows / Linux 上的 `Ctrl+Q`：Firefox、Chrome、多数 GTK/Qt 应用以它作为"退出"。热键注册失败或应用未运行时，用户按下会直接关闭当前应用。
- `Ctrl+Alt+Q`：Windows 把 Ctrl+Alt 视为 AltGr，德语等布局下这个组合用于输入 `@`。

最终默认值由原型阶段的三平台冲突测试决定，需要排查输入法、Spotlight、Raycast、ChatGPT 桌面端、Office 等常见占用。用户可以在设置中改回 `Ctrl+Q`，此时应提示上述风险。

**首次启动：** 必须让用户确认或更换快捷键，并实际按一次以验证注册成功。注册失败时（例如被占用、Wayland 不支持）给出明确提示和替代入口。

支持用户自定义快捷键，并具备快捷键录制、冲突检测和恢复默认设置等功能。

应提供以下入口：

- 全局快捷键。
- 系统菜单栏或托盘。
- 可选命令行入口。
- 后续可扩展其他启动器集成。

默认不采用双击修饰键等容易误触发的交互方式。

## 3.2 悬浮命令面板

界面参考 Spotlight、Raycast 等高效率启动器的交互方式，但应具有独立的产品设计。

基本要求：

- 快速唤起和关闭。
- 键盘操作优先。
- 支持搜索、选择、补全、预览、参数编辑和确认插入。
- 展示模板名称、别名、简介及参数提示。
- 尽量不影响用户当前工作窗口。macOS 上使用 non-activating panel（`NSPanel`）接收键盘输入，不让原应用失去激活状态；其他平台在原型阶段确定等效方案。
- 插入完成后自动关闭并恢复原应用输入焦点。
- 支持明暗主题，适配系统显示比例及不同分辨率。
- 面板窗口应常驻并预创建，唤起时只做显示，以满足 14.1 的延迟目标。

应追求轻量、流畅、符合系统习惯的体验，避免复杂布局影响主要操作效率。

## 3.3 智能搜索与提前确认（v0.2 修订）

支持：

- 模板名称搜索。
- 别名搜索。
- 前缀匹配。
- 模糊匹配。
- 拼写容错。
- 分类和标签检索。
- 最近使用、常用和收藏排序。

**匹配分层**（高层级总是排在低层级之前）：

1. 名称或别名精确匹配（不区分大小写）。
2. 名称或别名前缀匹配。
3. 模糊匹配 / 拼写容错。

**稳定排序：** 同一层级内依次按收藏、使用频率、字母序排序。使用频率在面板打开时取快照，输入过程中不更新，避免候选项跳动。

**Enter 语义：**

- 第 1、2 层存在匹配时，Enter 直接选中当前高亮项（例如只有 `review` 以 `rev` 开头时，输入 `rev` 即可确认）。
- 只有第 3 层（模糊）匹配时，第一次 Enter 只把命令补全为目标模板名，第二次 Enter 才插入，防止拼写容错导致误插入。

不应在用户尚未确认时自动执行模板。

完整的输入语法、参数解析和错误处理规则见 `docs/input-grammar.md`。

## 3.4 渐进式交互提示

命令面板应根据当前输入状态动态展示：

- 可能匹配的模板。
- 模板说明。
- 可用命令别名。
- 参数名称、类型、默认值和说明。
- 参数候选值。
- 当前补全建议。
- 下一步可以执行的键盘操作。

当用户输入 `r --` 时，应直接展示当前模板支持的参数。

当输入参数值时，应展示对应候选值、说明及默认值。

对缺少必填参数、无效参数或存在歧义的情况，应提供明确的反馈和修正入口。

中文输入法下键入的 `——`、`＝`、`，` 等全角符号在参数区内应被规范化识别（见语法规范），避免用户切换输入法。

新用户应能够在不阅读完整说明文档的情况下逐步学会使用。

## 3.5 键盘交互

建议默认交互：

| 按键 | 功能 |
|---|---|
| 唤起快捷键 | 唤起 / 切换面板 |
| ↑ / ↓ | 切换候选项 |
| Tab | 接受补全 / 进入参数 |
| Shift+Tab | 返回上一参数 |
| Enter | 确认并插入（模糊匹配时先补全，见 3.3） |
| Shift+Enter | 展开 Prompt 预览 |
| Esc | 返回 / 关闭 |
| 可配置快捷操作 | 复制、收藏、编辑等 |

实际键位应根据焦点状态设计，避免 Enter、Tab 在不同模式下产生不可预测的行为。各焦点状态下的按键行为应在交互状态说明中逐一列出。

提供可发现的快捷键提示，并支持高级用户定制。

# 4. Prompt 模板系统

## 4.1 模板基本信息

每个模板支持：

- 唯一标识。
- 名称。
- 一个或多个别名。
- 描述。
- 分类和标签。
- 模板正文。
- 参数定义。
- 默认参数。
- 可选预设。
- 创建及修改时间。
- 版本历史。
- 来源及作者信息（适用于社区模板）。

采用开放、可读、可迁移的模板数据格式。

允许高级用户直接编辑配置，同时提供图形化编辑器。

## 4.2 参数化模板

支持以下参数类型：

- 字符串。
- 布尔值。
- 枚举。
- 多选。
- 数值。
- 多行文本。
- 可选参数。
- 必填参数。

支持参数默认值、合法性校验、条件显示、参数依赖及互斥规则。

参数可声明为"位置参数"（只接受其候选值，见语法规范），并可声明单字母短名。

例如：

`review --strict --focus=security`

与图形界面中选择"严格审查"和"安全专项"应产生相同结果。两者都先归一为同一组参数值，再交给同一个渲染器。

## 4.3 模板渲染（v0.2 修订）

支持：

- 变量插值。
- 条件表达式。
- 可选内容片段。
- 循环或列表展开。
- 模板引用。
- 公共片段复用。
- 条件组合。
- 预设参数覆盖。
- 自定义附加文本。

**实现约束：**

- 正文使用成熟的模板引擎（Rust 侧首选 MiniJinja 或同类 Jinja 兼容引擎），不自研模板语言。
- 参数的类型、默认值、候选值、依赖（`requires`）和互斥（`conflicts`）在声明式 schema 中定义，并在渲染前校验，不放进模板正文逻辑。
- 渲染在沙箱中执行：禁止文件、网络、进程访问，限制递归深度和输出长度。

模板生成应具有确定性。相同模板及参数应生成相同结果，不需要 AI 参与。

## 4.4 Prompt 组合

支持将多个可复用的 Prompt 组件组合成完整模板。

例如：

`基础审查 + 安全检查 + 性能检查 + 中文输出`

组合功能应考虑内容重复、依赖关系、互斥条件及生成顺序。

优先提供简单清晰的组合体验，而不是要求普通用户学习复杂脚本语言。

## 4.5 模板管理

提供独立的模板管理界面，包含：

- 新建、编辑、复制、删除。
- 搜索、筛选、分类。
- 参数可视化配置。
- 实时渲染预览。
- 快捷命令测试。
- 收藏与使用历史。
- 批量导入导出。
- 历史版本查看与恢复。
- 冲突版本比较与合并。

提供模板修改前后的差异查看能力。

# 5. 内置优质 Prompt 模板库

## 5.1 设计目标

应用首次安装后应提供可直接使用的高质量 Prompt 模板，而不是空白模板管理器。

模板应优先服务 AI 编程场景，同时覆盖部分日常高频需求。

内置模板不仅要实用，还应充分展示产品的参数、条件、组合、补全和预设能力。

## 5.2 模板来源

参考公开、社区广受好评且经过实际使用验证的 Prompt 设计和开发工作流。

可研究：

- 开源 AI 编程项目中的成熟 Prompt。
- Claude Code、Codex、Cursor 等工具的社区实践。
- 高质量开发者提示词合集。
- 开源项目中的代码审查和调试流程。
- 公开的提示词工程最佳实践。

应优先保证实际质量，而不是追求模板数量。

可以对已有思路进行重新组织、抽象及适度改写，使其符合本产品的参数化结构。

必须注意原始材料的版权和许可证；保留必要的来源、署名及许可证信息。没有明确再分发授权的材料，不应直接复制进入内置模板库。

| `simplify` | 代码简化 | 精简复杂度 |
| `investigate` | 问题调查 | 搜集证据与评估假设 |

这些命令作为默认示例，允许用户修改、禁用或覆盖。

## 5.4 高质量标准

内置 Prompt 应当：

- 目标明确。
- 结构清晰。
- 提供必要约束。
- 避免无意义的冗长输出。
- 区分事实、推断与待验证事项。
- 鼓励先理解上下文，再采取行动。
- 避免未经请求的大范围修改。
- 根据任务类型提供不同的输出格式。
- 适合主流 AI 编程代理执行。

对于风险较高的操作，应提供只读分析、建议修改和允许执行等不同模式。

## 5.5 内置示例和引导

提供一组充分体现产品能力的示例：

- 简单模板：`zh`
- 多别名：`r / review`
- 布尔参数：`r --strict`
- 枚举参数：`r --scope=staged`
- 多选参数：`r --focus=security,performance`
- 自由文本参数。
- 模板组合。
- 预设模式。
- 条件渲染。
- AI 自然语言编辑。

首次启动时，通过少量可交互的示例帮助用户理解核心功能。

用户可以恢复官方默认模板，也可以独立维护自己的修改版本。

后续支持社区 Prompt Packs，以及可选择安装、更新和卸载的模板集合。

# 6. AI 辅助模板编辑

## 6.1 核心能力

内置 AI 模板编辑助手，允许用户通过自然语言管理模板。

支持：

- 根据描述创建新模板。
- 优化已有模板。
- 增加、删除或修改参数。
- 自动识别可参数化内容。
- 将长 Prompt 拆分为复用组件。
- 合并相似模板。
- 转换不同 AI 工具适用的版本。
- 根据反馈调整结构和输出要求。
- 生成模板说明、命令别名及示例。
- 检查模板是否存在矛盾或冗余。

AI 不应仅仅是一个普通聊天输入框，而应具备对模板结构的理解和编辑能力。AI 的输出必须是符合模板 schema 的结构化草稿，并在展示前通过 schema 校验和试渲染。

## 6.2 编辑体验

推荐交互：

1. 用户打开模板，选择 AI 编辑。
2. 输入自然语言修改要求。
3. AI 生成结构化修改草稿。
4. 系统展示修改摘要和具体差异。
5. 用户选择应用、继续调整或取消。
6. 确认后保存新版本。

AI 的任何修改都不得未经确认直接覆盖原模板。

必须支持撤销和版本恢复。

## 6.3 模型供应商（v0.2 修订）

按**协议**而不是按厂商实现，首版只实现两种协议：

| 协议 | 覆盖的服务 |
|---|---|
| OpenAI 兼容（Chat Completions） | OpenAI、DeepSeek、Ollama 等本地模型、多数中转与自定义 Endpoint |
| Anthropic Messages | Anthropic |

用户可添加多个"供应商配置"，每个配置包含：协议、Base URL、API Key、模型名、请求参数。

使用 BYOK（用户自带 API Key）模式。

可选支持 Cloudflare AI Gateway（作为一个 Base URL 即可），但不得强制所有 AI 请求经过官方服务器。

不应假设用户的 AI 聊天订阅自动提供 API 调用权限。

## 6.4 隐私要求与配置同步（v0.2 修订）

模板内容、工作区信息、选中文本及其他上下文不得在未经授权的情况下自动发送给 AI 服务。

用户应能够了解某次 AI 编辑准备提交哪些内容。

API 凭据在本机使用操作系统提供的安全存储机制（macOS Keychain、Windows Credential Manager、Linux Secret Service）。

**AI 配置同步（用户可选）：**

- 每个供应商配置单独提供"同步到其他设备"开关，**默认关闭**。
- 开启后，该配置（含 API Key）作为同步数据的一部分，按第 9 章端到端加密后上传；服务端无法解密。
- 到达其他设备后，API Key 同样存入该设备的系统安全存储。
- Base URL 等字段支持"同步默认值 + 本机覆盖"。例如 Ollama 的 `localhost` 地址只对某台设备有效。
- 开启同步时应明确提示：任何已授权设备都能取得该 Key；撤销设备后，需要用户自行到供应商处作废并更换 Key（见 9.5）。

AI 功能关闭或未配置时，不应影响核心使用体验。

# 7. 跨应用输入与上下文

## 7.1 跨应用输入

支持将生成的 Prompt 插入当前应用的文本输入位置。

主要目标软件：

- macOS Terminal、iTerm2、cmux。
- Windows Terminal、PowerShell。
- Linux 常见终端。
- Claude Code。
- Codex CLI。
- Cursor。
- VS Code。
- 主流浏览器。
- 常见文本编辑器。

插入完成后应尽量恢复原来的应用焦点和输入位置。

默认只插入文本，不自动提交或发送。

## 7.2 输入兼容性（v0.2 修订）

**插入方式：** 通过剪贴板 + 模拟粘贴快捷键插入，**不使用逐字模拟键入**。逐字键入时多行文本中的换行会被终端或 AI 代理当作回车提交，违反"默认不提交"原则；粘贴可以利用终端的 bracketed paste，并且速度和 Unicode 兼容性更好。

**剪贴板保护：**

1. 备份当前剪贴板全部格式。
2. 写入 Prompt，并标记为临时/隐藏内容，避免进入剪贴板管理器历史（macOS：`org.nspasteboard.TransientType` / `ConcealedType`；Windows：剪贴板历史与云剪贴板排除格式；Linux 视桌面环境而定）。
3. 发送粘贴快捷键。
4. 延迟后恢复原剪贴板。如果期间剪贴板已被其他程序修改，就不覆盖。

**焦点：** 面板不抢占原应用的激活状态（见 3.2）；插入前确认目标窗口仍是唤起时的窗口，否则改为复制并提示，避免插入到错误应用。

**平台限制：**

- macOS：模拟粘贴需要"辅助功能"权限，按需请求并说明用途。
- Windows：以管理员身份运行的窗口会拒收普通权限进程的模拟输入（UIPI）。检测到这种情况时降级为复制并提示，不要求本应用以管理员身份运行。
- Linux：见 10.3。

**无权限降级模式：** 未授予输入权限或自动插入不可用时，选中模板后将结果复制到剪贴板，并提示用户手动粘贴（如 `⌘V` / `Ctrl+V`）。该模式必须完整可用，保证新用户不授权也能完成首次使用。

应重点测试：

- 长文本粘贴。
- 多行文本。
- Unicode、中文及特殊符号。
- 终端输入（含 Claude Code、Codex CLI 等 TUI）。
- 剪贴板历史内容保护。
- 焦点恢复。
- 应用切换竞态。
- 不支持自动输入的特殊窗口。

不得为了自动粘贴而默认要求管理员或系统最高权限。

## 7.3 可选上下文感知

后续支持识别：

- 当前前台应用。
- IDE 工作区。
- Git 仓库。
- 当前分支。
- 当前文件或选中文本。
- 当前运行的 AI 编程工具。
- 本地或远程终端会话。

支持全局、应用级和项目级模板配置。

例如同一个 `review` 命令，在不同项目中使用不同的审查规范。

上下文识别应采用明确的权限边界，不能假设所有终端都能够直接获取工作目录。

SSH 远程工作区需要独立的可选集成方案。

上下文访问应遵循最小权限原则，默认不进行不必要的后台扫描。

# 8. 本地优先与数据管理

## 8.1 Local-first

本地数据是用户日常操作的直接数据来源。

所有核心操作，包括搜索、模板渲染、参数补全、插入、编辑和预览，均应在离线状态下正常工作。

云端同步不得成为打开面板或生成 Prompt 的前置条件。

网络异常不能阻塞主要交互。

## 8.2 数据可移植性

采用开放、版本化的数据格式。

支持：

- 本地导入导出。
- 单模板导出。
- 完整备份。
- 加密备份。
- 历史版本恢复。
- 后续 Git 管理或同步集成。

用户应能够在不依赖官方服务器的情况下长期保存和迁移自己的数据。

# 9. Cloudflare 端到端加密同步

## 9.1 同步模式

提供以下模式：

**纯本地模式**

不需要账号、不需要云端，安装后即可使用全部基础功能。

**自托管同步模式**

用户可以部署自己的 Cloudflare 同步服务。

**可选公共同步服务**

未来可以提供官方托管服务，但不得成为唯一同步途径。

同步协议及服务端实现应开源，避免供应商锁定。

## 9.2 基础架构（v0.2 修订）

同步分为两个独立的工作项，分别设计、估算和测试：

**A. 同步服务端（Cloudflare）**

- Cloudflare Workers + Hono：同步 API。
- Cloudflare D1 + Drizzle：存储密文记录、版本信息和设备记录。
- Durable Objects：仅在确有实时同步需求时使用。

可复用现有 Cloudflare 项目（如 `nekro-nxt-community`）的工程骨架：

| 可复用 | 用途 |
|---|---|
| Hono + D1 + Drizzle + 迁移体系 | 服务端骨架 |
| 带 PKCE 的 OAuth 授权码流程 | 桌面端通过浏览器回调登录 |
| 授权记录的 access/refresh 令牌哈希轮换与撤销 | 设备授权与撤销 |
| 写入限流、审计日志 | 防滥用与审计 |

**禁止复用**任何服务端持有主密钥的加解密实现（例如以服务端环境变量密钥加密配置的模块）。该模型下服务端能解密数据，违反 9.3。用户数据的加解密只能发生在客户端。

服务端只负责身份认证、存储、变更分发、版本协调及同步状态管理。

**B. E2EE 客户端（Rust 核心）**

负责密钥层级、加解密、设备配对、密钥轮换、离线修改队列、冲突检测与保留。这是同步功能的主要工作量所在。

## 9.3 端到端加密

**这是强制要求，而非可选功能。**

所有需要同步的私有模板内容和用户配置（包括用户选择同步的 AI 配置及 API Key）必须在本地加密，然后才允许上传服务器。

具体要求：

1. 加密密钥由客户端安全生成和管理。
2. 服务端不持有可解密用户内容的密钥。
3. 服务端不能自行还原模板正文、参数或其他受保护内容。
4. 解密只在已授权客户端本地完成。
5. 使用成熟、经过安全审查的加密库与构造（如 libsodium 的 XChaCha20-Poly1305 / secretstream、X25519），不自行组合密码学原语。
6. 所有密文应具有完整性保护，防止未经授权的修改；记录 ID、版本号等作为关联数据（AAD）参与认证，防止密文被替换或重放到其他记录。
7. 支持密钥轮换和协议版本演进（密文携带格式版本和密钥版本）。
8. 模板名称、别名、标签等私有元数据全部放在密文内。
9. **服务端记录 ID 使用客户端生成的随机值**，不得从模板名、别名或内容派生。服务端只保存 `(opaque_id, version, device_id, ciphertext, updated_at, deleted)` 这类最少字段。
10. 不允许将敏感明文或密钥写入日志及错误报告。

应明确区分端到端加密与普通传输加密。

TLS 只能保护传输链路，不能代替客户端加密。

即使 Cloudflare 数据库内容或服务端权限泄漏，攻击者也不应仅凭服务端持有的数据恢复用户模板明文。

需要明确说明服务端仍可能观察到的有限元数据，例如账号身份（如使用 GitHub 登录）、设备连接、记录数量、密文大小及同步时间。

**建议的密钥层级：**

- **Vault Key：** 随机生成的对称密钥，加密所有同步记录。
- **设备密钥对：** 每台设备生成，私钥存于系统安全存储；Vault Key 以设备公钥包装后分发。
- **恢复密钥：** 用户保存的高熵恢复短语，用于包装一份 Vault Key 备份。

## 9.4 多设备授权

支持安全、简洁的设备配对流程。

优先考虑：

- 已授权设备生成配对二维码或一次性配对信息。
- 新设备验证配对信息。
- 通过经过认证的安全密钥交换机制获得 Vault Key（配对码需能防中间人，例如配对码包含公钥指纹或使用 PAKE）。
- 新设备完成同步。

设备授权和解密密钥管理应分离于单纯的云服务登录认证。

不得仅凭服务器账号或普通登录 Token 就允许解密历史数据。

**自托管认证：** 除 OAuth 登录外，提供不依赖第三方 OAuth 的认证方式（例如以设备密钥签名认证），让自托管用户无需额外创建 OAuth 应用。

## 9.5 密钥管理与恢复

密钥默认保存在各操作系统提供的安全凭据存储中。

支持用户控制的恢复密钥或恢复短语。

需要设计：

- 新设备添加。
- 设备移除。
- 设备遗失。
- 主密钥恢复。
- 密钥轮换。
- 加密备份。
- 无法恢复密钥时的数据处理。

系统应清楚告知：在真正的零知识设计下，如果所有已授权设备和恢复材料均丢失，服务端无法帮助恢复明文。

设备撤销后应禁止其获取新的同步授权，轮换 Vault Key 并重新加密后续数据；不能承诺远程删除设备已经解密并保存的历史内容。

**撤销设备时，若存在已同步的 AI 配置**，应列出受影响的供应商配置，提示用户到对应供应商处作废并更换 API Key。轮换 Vault Key 无法保护已被该设备取得的 Key。

## 9.6 同步体验

支持：

- 自动后台同步。
- 手动立即同步。
- 增量变更同步。
- 离线编辑。
- 网络恢复后自动续传。
- 多设备变更检测。
- 冲突版本保留。
- 冲突可视化比较。
- 版本历史。
- 删除同步。
- 同步状态与错误提示。

对于同一模板的并发修改，不允许简单、静默地覆盖其中一方。冲突以"单条记录"为粒度检测：服务端拒绝基于过期版本的写入，客户端在本地保留双方版本并交给用户合并。首版不引入 CRDT。

同步不得明显影响命令面板的启动和搜索速度。

## 9.7 同步范围（v0.2 修订）

建议同步：

- 模板及正文。
- 参数定义和预设。
- 分类、标签、收藏。
- 用户模板配置。
- AI 编辑产生的已确认版本。
- 用户可同步的偏好设置。

**用户可选同步（默认关闭）：**

- AI 供应商配置及 API Key（按供应商单独开关，见 6.4）。

默认不跨设备同步：

- 系统权限状态。
- 全局快捷键。
- 设备特定的窗口及显示配置。
- 本机工作区路径。
- 未经用户允许的敏感历史记录。

允许用户明确选择同步的数据范围。

# 10. 跨平台体验

## 10.1 目标平台

正式面向：

- macOS。
- Windows 10/11，优先 Windows 11。
- Linux，优先主流 GNOME / KDE 桌面环境。

各平台共享统一的模板能力、配置格式、同步协议和核心交互逻辑。

可以针对不同系统独立实现窗口、输入、权限和快捷键相关功能。

**不得为了统一代码而明显牺牲某个平台的主要使用体验。**

## 10.2 技术选型原则

优先考虑共享的 Rust 核心和跨平台桌面架构。

Tauri 2 可以作为重点候选，但不应未经验证就确定最终方案。

要求先制作真实交互原型，比较：

- 全局快捷键可靠性。
- 悬浮窗口体验（含 macOS non-activating panel）。
- 跨应用文本插入。
- 启动与唤起速度（预创建隐藏窗口时能否达到 150ms 目标）。
- 后台资源占用。
- 系统权限管理（含未签名应用的权限持久性，见 12.2）。
- UI 原生感。
- 构建和维护成本。

必要时使用平台专属原生模块，甚至独立实现关键窗口层。

## 10.3 Linux 兼容性

明确处理 X11 和 Wayland 的差异：

- **全局热键：** Wayland 下依赖 xdg-desktop-portal GlobalShortcuts，可用性取决于桌面环境及其版本。
- **文本注入：** Wayland 没有通用方案。`wtype` 仅适用于支持 virtual-keyboard 协议的合成器；`ydotool` 需要 uinput 权限；RemoteDesktop portal 需要用户授权。
- **窗口：** Wayland 下应用无法自行控制浮窗位置和焦点切换。

首版建议承诺：X11 及 KDE / GNOME 下的"热键唤起 + 复制到剪贴板"。Wayland 自动粘贴标注为实验性。

对于不支持全局热键或跨应用输入的桌面环境，应提供可发现的替代操作（托盘、CLI、桌面环境自定义快捷键调用 CLI），并明确标注兼容状态。

不应声称所有 Linux 发行版和窗口管理器具备相同能力。

建立公开的平台兼容性矩阵。

# 11. 界面与视觉设计

## 11.1 设计原则

- 简洁、现代、轻量。
- 键盘优先。
- 信息密度适中。
- 清楚展示当前状态和下一步操作。
- 主要操作不依赖鼠标。
- 不滥用动画和视觉装饰。
- 符合各平台交互习惯。
- 兼容明暗主题和高 DPI 显示。

## 11.2 主要界面

**Launcher**

高频使用的轻量命令面板，负责搜索、参数输入、预览和插入。

**Template Library**

用于浏览、搜索、分类及管理模板。

**Template Editor**

提供正文编辑、参数定义、实时预览及示例测试。

**AI Editor**

通过对话和结构化差异预览完成 AI 辅助修改。

**Settings**

管理快捷键、外观、同步、设备、模型供应商（含同步开关）、隐私及平台权限。

**Onboarding**

引导用户完成快捷键确认、输入权限授权（可跳过，跳过后使用无权限降级模式）以及首次模板使用。

不应强制用户完成云端同步或 AI 配置才能开始使用。

## 12.2 macOS 分发（v0.2 修订）

**现状：** 当前没有 Apple Developer ID 证书，项目成型后再评估购买。

**签名：** 使用一个**固定的自签名代码签名证书**签名所有发布版本，不使用每次构建都会变化的 ad-hoc 签名。

- 目的：系统"辅助功能"等隐私授权与应用签名身份绑定。签名身份不变，应用更新后授权才能保留；否则用户每次更新都要重新授权。
- 该行为必须在原型阶段实测验证（授权 → 更新版本 → 检查授权是否仍有效）。
- 证书私钥纳入发布流程的密钥管理并离线备份。私钥丢失会让所有用户的授权失效一次。

**Gatekeeper：** 未公证应用首次打开会被拦截。安装文档须如实说明"系统设置 → 隐私与安全性 → 仍要打开"的步骤及原因。不得把关闭系统安全保护作为正常安装步骤。

**Homebrew：** 使用自有 Homebrew Tap。Homebrew 对未签名 / 隔离属性的处理在持续收紧（`--no-quarantine` 已弃用），Tap 的安装与升级行为须以发布时的 Homebrew 版本实测为准，并写入文档。

**无权限降级：** 见 7.2。用户不授予辅助功能权限也能通过复制模式使用全部核心功能。

**未来迁移：** 改用 Developer ID 签名并公证后，签名身份变化会导致用户需要重新授权一次，须在发布说明中提前告知。

## 12.3 Windows 分发

提供适合普通用户的安装包。

优先考虑：

- GitHub Releases。
- WinGet。
- 可选便携版本。

应评估 Windows 应用签名、SmartScreen、更新和安装权限问题。

## 12.4 Linux 分发

根据目标发行版支持合适的安装方式：

- AppImage。
- deb。
- rpm。
- Flatpak（视权限与兼容性评估）。
- 社区包管理器。

优先保证可以稳定安装和正常使用，不必首版覆盖所有发行版。

## 12.5 版本更新

支持版本检查、更新提示和发布说明。

更新过程应保护本地模板、同步密钥、用户配置和历史数据。

不得未经用户确认进行破坏性数据迁移。

# 13. 安全与隐私

应用可能涉及剪贴板、辅助功能权限、工作区信息及 API 凭据，因此需要明确安全边界。

要求：

- 遵循最小权限原则。
- 按需请求系统权限。
- 对权限用途提供用户可理解的说明。
- 不进行隐蔽的系统输入监控。
- 不默认读取或上传剪贴板历史。
- 不自动将用户内容上传至 AI 服务。
- 不在日志中记录完整 Prompt 或敏感凭据。
- 插件及自定义脚本应受到明确的权限约束。
- 对外部导入模板采用安全解析机制。
- 不允许模板文件未经授权自动执行任意代码（模板渲染沙箱见 4.3）。
- 默认不启用用户行为追踪。
- 如未来加入遥测，应采用明确的选择加入机制。

用户应能够查看、导出和删除自己的本地数据及云端密文记录。

# 14. 性能与可靠性

## 14.1 性能目标

应用应当给用户接近即时响应的主观体验。

需要重点优化：

- 常驻内存占用。
- 空闲 CPU 使用率。
- 全局快捷键响应。
- 命令面板显示速度。
- 模板搜索延迟。
- 参数解析和渲染速度。
- 长 Prompt 插入稳定性。
- 后台同步资源消耗。

建议将普通硬件上的快捷键唤起到可输入状态控制在约 150ms 内作为性能优化目标，实际指标通过跨平台测试验证。

不应因为同步、AI 请求或后台更新阻塞主要交互。

## 14.2 稳定性要求

必须覆盖：

- 网络断开。
- API 不可用。
- 输入权限缺失。
- 目标软件失去焦点。
- 剪贴板被其他应用修改。
- 模板格式错误。
- 参数不合法。
- 同步冲突。
- 设备密钥缺失。
- 数据格式升级。
- 应用异常退出。
- 多屏及不同缩放比例。

错误反馈应当简洁明确，并提供可执行的恢复路径。

# 17. 核心验收标准

项目完成时，应重点验证以下体验。

### 17.1 快捷操作

用户在任意受支持的软件中按下唤起快捷键，输入 `r`，按下 Enter，即可成功插入预设代码审查 Prompt。

过程不需要鼠标、不需要等待网络、不需要打开模板管理器。

插入多行 Prompt 到 Claude Code、Codex CLI 等终端程序时不会被自动提交。插入后用户剪贴板恢复为原内容，且 Prompt 不出现在剪贴板管理器历史中。

### 17.2 智能发现

用户输入部分模板名称即可获得准确结果。

输入 `--` 时能够看到参数提示，不需要事先记住参数名称。

在中文输入法状态下键入 `——` 同样可以触发参数提示。

### 17.3 参数化

用户能够通过简短命令和可视化界面生成相同的复杂 Prompt。

参数错误时获得明确提示。

### 17.4 AI 修改

用户可以用自然语言要求 AI 为模板新增功能。

AI 能生成正确的模板结构，展示修改差异，并在用户确认后保存。

### 17.5 端到端加密同步

用户在设备 A 创建模板，设备 B 授权后能够解密同步的数据。

Cloudflare 服务端无法凭其持有的数据和凭据自行解密模板内容或已同步的 AI 配置。

服务端数据库中不出现模板名、别名、标签等明文。

设备离线编辑后能够恢复同步；冲突数据不会静默丢失。

### 17.6 跨平台

macOS 和 Windows 具备同等级的核心体验。

Linux 在受支持桌面环境中提供完整功能，对不可用的系统能力提供明确的兼容说明和降级操作。

### 17.7 开源安装

用户能够通过公开文档提供的安装方式完成部署。

安装流程清楚说明各平台的签名、权限及安全限制。

macOS 上应用更新后，已授予的辅助功能权限仍然有效。

### 17.8 新用户体验

首次安装后，用户无需创建模板、配置 API、注册账号或授予输入权限，即可通过内置模板完成实际操作。

# 18. 开发执行要求

本项目计划主要由 AI 编程代理自主完成设计、实现、测试和迭代。

开发过程中应遵循以下要求：

1. 优先产出完整产品设计，而不是直接开始堆叠代码。
2. 调研成熟竞品，提取值得借鉴的交互设计和实现经验。
3. 对跨平台窗口、快捷键和文本插入等高风险能力优先制作可运行原型。
4. 根据原型结果决定最终技术架构，不因开发便利而牺牲用户体验。
5. 将模板引擎、输入语法解析、同步协议、加密机制及系统输入适配设计为可独立测试的模块。
6. 建立自动化测试、构建、发布和回归验证流程。
7. 不得仅依赖代码审查判断 GUI 或系统级功能是否正常，必须进行真实操作系统上的交互测试。AI 代理难以独立完成的三平台真机测试，应列出由人工执行的测试清单及执行时机。
8. 为项目建立清晰的需求、架构、设计决策及已知限制文档。
9. 以可维护性、正确性和稳定性优先，不追求未经验证的复杂设计。
10. 保持产品轻量，避免与核心价值无关的功能膨胀。

## 期望交付内容

在正式开发前，完成：

- 竞品与技术可行性研究。
- 完整产品设计方案。
- 关键用户旅程与交互状态说明。
- 主要界面视觉设计。
- 跨平台技术选型报告。
- 同步及端到端加密安全设计。
- 模板数据规范。
- 输入语法规范（初稿见 `docs/input-grammar.md`）。
- 功能优先级和阶段开发计划。
- 测试策略与验收标准。

在上述设计完成并确认主要技术风险后，按阶段自主实现、测试和迭代。

**最终目标：打造一款轻量、快速、可靠、跨平台、开放且隐私友好的 Prompt 效率工具，让高频 AI 用户能够以极低的操作成本管理、组合和使用自己的提示词。**

# 19. 待决事项（v0.2 新增）

以下是评审中提出、尚未决定的建议，记录在此以备后续讨论：

1. **本地存储采用"一个模板一个纯文本文件"**（Markdown + YAML frontmatter）。好处：天然支持 Git 版本管理和导入导出，项目级 Profile 可直接用仓库内 `.prompts/` 目录实现，AI 编程代理可以直接编辑。需要考虑：与 E2EE 同步记录模型的映射，以及外部修改检测。
2. **先做 1–2 周插入链路原型，再完成全部设计交付物**：热键 → 浮窗 → 粘贴 → 焦点恢复 → 自签名授权持久性。原型结果可能改变技术选型和 P0 范围。
3. **提供 CLI / MCP server**，让用户已有的 AI 编程代理可以直接读写模板，作为内置 AI 编辑器的补充。
4. **首批内置模板数量**：建议先做 5–8 个，每个附真实任务的对比验证记录，再逐步扩充。
5. **默认快捷键最终取值**：方向已定为"Q 系"（macOS `⌃Q`，Windows / Linux `Alt+Q`），具体组合待原型阶段的三平台冲突测试确定。
6. **开源许可证选择**：影响能否参考 GPL 项目的实现。
